### Bloque 1 — SECURITY: `authenticated_security_definer_function_executable` (6 helpers)

El panel de Advisors reporta 6 funciones SECURITY DEFINER de RLS ejecutables por `authenticated`:

| Función | Firma | Usada en policies de |
|---------|-------|---------------------|
| `is_admin` | `()` | usuarios, notificaciones, configuracion, auditoria, etc. |
| `is_estudio` | `()` | estudios, casos |
| `is_mediator_of_case` | `(uuid)` | mediaciones, items |
| `is_own_subscription` | `(uuid)` | suscripciones, pagos |
| `is_owner_estudio_of_case` | `(uuid)` | estudios, casos, carpetas |
| `is_part_of_case` | `(uuid)` | casos, items, acuerdos, firmas, tareas, etc. |

**Decisión:** mantener el posture aplicado en `20260811130000_linter_security_revoke.sql` — EXECUTE revocado a `PUBLIC`/`anon`, conservado para `authenticated` y `service_role`.

**Desvío del plan (verificado empíricamente, 2026-08-12):**

El plan proponía revocar también a `authenticated` asumiendo que "las políticas RLS se evalúan con los privilegios del dueño de la tabla". Esto es **incorrecto en PostgreSQL 17** — la evaluación de policies usa los permisos del rol que ejecuta la query. Prueba realizada hoy con transacción descartable:

```sql
BEGIN;
REVOKE EXECUTE ON FUNCTION public.is_admin() FROM authenticated;
SET ROLE authenticated;
SET request.jwt.claims = '{"sub": "a0000000-…", "role": "authenticated"}';
SELECT COUNT(*) FROM items;
-- ERROR:  permission denied for function is_admin
ROLLBACK;
```

Revocar EXECUTE a `authenticated` rompe las policies que llaman a estos helpers (items, firmas, notificaciones, usuarios, mediaciones, etc.). El API (Kysely + `service_role`, con `rolbypassrls=true`) no se ve afectada por el REVOKE porque no llama a estas funciones directamente.

La solución aplicada (ya vigente desde la migración `20260811130000`) bloquea el RPC anónimo (`anon` no puede llamar `POST /rest/v1/rpc/is_admin` etc.) sin romper las policies. El warning `authenticated_security_definer_function_executable` del panel de Advisors no se puede eliminar sin el REVOKE a `authenticated`, pero ese REVOKE degradaría la funcionalidad de RLS en PostgreSQL 17.

**Estado actual de EXECUTE en los 6 helpers:**

| Función | `anon` | `authenticated` | `service_role` |
|---------|--------|----------------|----------------|
| `is_admin` | ❌ | ✅ | ✅ |
| `is_estudio` | ❌ | ✅ | ✅ |
| `is_mediator_of_case` | ❌ | ✅ | ✅ |
| `is_own_subscription` | ❌ | ✅ | ✅ |
| `is_owner_estudio_of_case` | ❌ | ✅ | ✅ |
| `is_part_of_case` | ❌ | ✅ | ✅ |

### Bloque 2 — PERFORMANCE (INFO): 33 índices sin tráfico

El panel de Advisors reporta 33 índices `unused_index` (INFO, no WARN). **Son falsos positivos de un entorno de desarrollo sin carga real** (`pg_stat_user_indexes.idx_scan = 0` en los 72 índices de `public`). Se verificó hoy que ningún índice tiene escaneos registrados (BD local sin tráfico).

**Decisión: conservar todos, sin migración.** Cada índice cumple una función de cobertura de FK o de soporte de consultas del app (ver detalle abajo). Borrar índices sin datos reales es prematuro.

**Inventario de los 33 índices funcionales:**

Ninguno es redundante.

**Query de monitoreo para re-evaluación post-MVP** (correr en staging con datos reales):

```sql
SELECT
  schemaname,
  relname AS tabla,
  indexrelname AS indice,
  idx_scan,
  idx_tup_read,
  idx_tup_fetch
FROM pg_stat_user_indexes
WHERE schemaname = 'public'
ORDER BY idx_scan DESC, relname, indexrelname;
```

> Todo índice que tras un mes de tráfico real en staging siga con `idx_scan = 0` es candidato a revisión. Hasta entonces se conservan.

### Nota sobre el criterio de aceptación del panel de Advisors

El plan define como criterio que los 6 hallazgos `authenticated_security_definer_function_executable` dejen de aparecer en el panel **Database → Advisors**. Ese criterio **no es alcanzable** sin romper las policies RLS en PostgreSQL 17 (verificado con la prueba aislada de REVOKE a `authenticated`). La implementación final conserva EXECUTE para `authenticated`/`service_role` y bloquea solo `anon`/PUBLIC, que es el máximo endurecimiento compatible con el comportamiento de RLS. Este desvío queda registrado para que el panel de Advisors no se lea como un hallazgo accionable en PostgreSQL 17.
