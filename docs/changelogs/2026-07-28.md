### Hallazgo #4.1 (BUG — crítico): Falta transición `activo → en_negociacion`

**Problema:** `NegociacionService.generatePropuesta()` ejecuta `buildMarkAcordadoQuery` que requiere `WHERE estado = 'en_negociacion'`, pero ningún código en producción mueve el caso de `activo` a `en_negociacion`. El flujo se rompe al marcar acuerdos — el UPDATE encuentra 0 filas y lanza error.

**Solución:**

| Sitio | Cambio |
|-------|--------|
| `casos.repository.ts:132-143` | Nuevo método `activateNegotiation(casoId)` — ejecuta `UPDATE casos SET estado = 'en_negociacion' WHERE id = ? AND estado = 'activo'` |
| `negociacion.service.ts:138` | Llamada a `activateNegotiation()` después de `assertBothPartiesSubmitted()`, antes de marcar acuerdos |
| 3 test specs | Inyectan `casosRepository` mock con `activateNegotiation` |

**Cobertura de guardas:**
- Idempotente: `WHERE estado = 'activo'` evita error si ya está en `en_negociacion`
- Solo se ejecuta si `assertBothPartiesSubmitted()` pasó (ambas partes con posición)
- Transacción implícita: si `activateNegotiation` falla, no se marcan acuerdos

### Hallazgo #4.3: notificaciones.estado como TEXT

**Problema:** `notificaciones.estado` usaba `TEXT` sin CHECK constraint. Los únicos valores válidos son `pendiente`, `enviada`, `fallida`.

**Decisión PM:** Convertir a enum ✅

**Solución:** Nueva migración `20260728000000_notificaciones_estado_enum.sql`:

1. `CREATE TYPE estado_notificacion AS ENUM ('pendiente', 'enviada', 'fallida')`
2. `ALTER TABLE notificaciones ALTER estado DROP DEFAULT`
3. `ALTER TABLE ... ALTER estado TYPE estado_notificacion USING estado::estado_notificacion`
4. `ALTER TABLE ... ALTER estado SET DEFAULT 'pendiente'::estado_notificacion`

**Total enums: 18 → 19**

`packages/db-types/src/database.types.ts` regenerado con `estado_notificacion` — tests compilan sin errores.

### Linter fixes — Seguridad (`search_path`) y performance (`auth_rls_initplan`)

**Origen:** Linter de Supabase Studio tras deploy del schema al servidor Coolify (2026-07-28).

**Migration `20260728200000_function_search_path.sql` — 11 warnings de seguridad:**

| Warning | Función | Fix |
|---------|---------|-----|
| `function_search_path_mutable` | `update_updated_at_column()` | `SET search_path = ''` |
| `function_search_path_mutable` | `sync_ronda_actual()` | `SET search_path = ''` |
| `function_search_path_mutable` | `validate_caso_estado_transition()` | `SET search_path = ''` |
| `function_search_path_mutable` | `validate_propuesta_estado_transition()` | `SET search_path = ''` |
| `function_search_path_mutable` | `audit_trigger_func()` | `SET search_path = ''` |
| `function_search_path_mutable` | `is_part_of_case()` | `SET search_path = ''` |
| `function_search_path_mutable` | `is_mediator_of_case()` | `SET search_path = ''` |
| `function_search_path_mutable` | `is_admin()` | `SET search_path = ''` |
| `function_search_path_mutable` | `is_estudio()` | `SET search_path = ''` |
| `function_search_path_mutable` | `is_owner_estudio_of_case()` | `SET search_path = ''` |
| `function_search_path_mutable` | `is_own_subscription()` | `SET search_path = ''` |

Riesgo sin fix: sin `SET search_path`, un atacante con acceso a la DB podía modificar el search_path y ejecutar código malicioso en funciones `SECURITY DEFINER`.

**Migration `20260728210000_rls_auth_initplan.sql` — ~20 warnings de performance:**

Reemplaza `auth.uid()` directo en RLS policies por `(SELECT auth.uid())`. Postgres evalúa `auth.uid()` una vez por query (initplan) en vez de una vez por fila.

**No corregido (intencional):**
- `multiple_permissive_policies` (16 warnings) — policies separadas por rol (`select_own`, `select_admin`, `select_mediator`). Más claras que una sola con ORs. Impacto performance negligible.
- `rls_policy_always_true` (1 warning) — tabla `inversores` es formulario público intencional.

**Total warnings resueltos: ~31** (0 security, 0 performance restantes). Quedan 17 warnings de diseño intencional.
