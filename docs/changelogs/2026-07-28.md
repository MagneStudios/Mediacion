### Hallazgo #4.1 (BUG — crítico): Falta transición `activo → en_negociacion`

**Problema:** `NegociacionService.generatePropuesta()` ejecuta `buildMarkAcordadoQuery` que requiere `WHERE estado = 'en_negociacion'`, pero ningún código en producción mueve el caso de `activo` a `en_negociacion`. El flujo se rompe al marcar acuerdos — el UPDATE encuentra 0 filas y lanza error.

**Solución:**

| Sitio | Cambio |
|-------|--------|
| `casos.repository.ts:132-143` | Nuevo método `activateNegotiation(casoId)` — ejecuta `UPDATE casos SET estado = 'en_negociacion' WHERE id = ? AND estado = 'activo'` |
| `negociacion.service.ts:138` | Llamada a `activateNegotiation()` después de `assertBothPartiesSubmitted()`, antes de marcar acuerdos |
| 3 test specs | Inyectan `casosRepository` mock con `activateNegotiation` |

**Cobertura de guardas:**
- Idempotente: `WHERE estado = 'activo'` evita error si ya está en `en_negociacion`
- Solo se ejecuta si `assertBothPartiesSubmitted()` pasó (ambas partes con posición)
- Transacción implícita: si `activateNegotiation` falla, no se marcan acuerdos

### Hallazgo #4.3: notificaciones.estado como TEXT

**Problema:** `notificaciones.estado` usaba `TEXT` sin CHECK constraint. Los únicos valores válidos son `pendiente`, `enviada`, `fallida`.

**Decisión PM:** Convertir a enum ✅

**Solución:** Nueva migración `20260728000000_notificaciones_estado_enum.sql`:

1. `CREATE TYPE estado_notificacion AS ENUM ('pendiente', 'enviada', 'fallida')`
2. `ALTER TABLE notificaciones ALTER estado DROP DEFAULT`
3. `ALTER TABLE ... ALTER estado TYPE estado_notificacion USING estado::estado_notificacion`
4. `ALTER TABLE ... ALTER estado SET DEFAULT 'pendiente'::estado_notificacion`

**Total enums: 18 → 19**

`packages/db-types/src/database.types.ts` regenerado con `estado_notificacion` — tests compilan sin errores.
