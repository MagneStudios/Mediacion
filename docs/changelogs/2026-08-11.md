### Bloque 1 — Security: REVOKE EXECUTE + hardening de `inversores`

- **Funciones de trigger** (`assign_caso_codigo`, `audit_trigger_func`, `handle_new_user`): EXECUTE revocado a `PUBLIC`, `anon` y `authenticated`. Los triggers corren con permisos del dueño de la tabla, ningún rol del request los necesita.
- **Helpers RLS** (`is_admin`, `is_estudio`, `is_mediator_of_case`, `is_own_subscription`, `is_owner_estudio_of_case`, `is_part_of_case`): EXECUTE revocado a `PUBLIC`/`anon` (cierra el RPC anónimo) y conservado para `authenticated` + `service_role`.
  - **Desvío del plan (verificado empíricamente):** el plan asumía que las policies RLS se evalúan como dueño de la tabla y que se podía revocar a `authenticated`. En **PostgreSQL 17** el EXECUTE de una función dentro de una policy se chequea contra el rol que ejecuta la query → revocar a `authenticated` rompe las policies. Se bloquea solo `anon`/PUBLIC.
- **`inversores_insert_anon`**: `WITH CHECK (true)` → validación básica (`nombre` y `email` no vacíos, formato email). La SELECT de `inversores` no se tocó.

### Bloque 2 — Performance: consolidación de policies SELECT

Una sola policy SELECT por tabla con `OR` (antes 2-3 separadas por rol):

| Tabla | Antes | Después |
|-------|-------|---------|
| `firmas` | `firmas_select_case` + `firmas_select_own` | `firmas_select` (own | part_of_case | admin) |
| `items` | `items_select_admin` + `items_select_mediator` + `items_select_own` | `items_select` (admin | mediator | own) |
| `notificaciones` | `notificaciones_select_admin` + `notificaciones_select_own` | `notificaciones_select` (admin | own) |
| `usuarios` | `usuarios_select_admin` + `usuarios_select_own` | `usuarios_select` (admin | own) |

- `is_admin()` como InitPlan `(SELECT is_admin())` se conserva.
- `firmas_select` preserva el branch `is_admin()` que tenía `firmas_select_case` (desvío menor del SQL literal del plan, para mantener resultados idénticos).
